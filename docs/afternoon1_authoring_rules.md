  直すときは §3 Step 2 の照合を先に行い、データ修正だけで1コミットにする。

- セッション開始時に `git pull origin main`。

アプリ内に載るのは **公式設問文＋図表＋解答欄＋解説**。問題本文は PDF を開いて読む前提。

|---|---|---|---|


## 2. rowKey — 全体の要

```
rowKey = `${s}|${q ?? ''}|${t ?? ''}`      （makeRowKey(s, q, t) と同一）
```

`officialAnswers.ts` の対象 id の `answers[]` の **全行と完全一致**させる（欠落も余剰も不可）。
設問文・行解説・設問別詳細解説の3つが、この1本のキーで結ばれている。

例（R6-G1-1 の11行）:

```
1|(1)|      1|(2)|ア    1|(2)|イ    1|(3)|
2|(1)|ウ    2|(1)|エ    2|(2)|      2|(3)|    2|(4)|
3|(1)|      3|(2)|
```

- `{ s:'1', q:'(1)' }` → `1|(1)|`
- `{ s:'1', q:'(2)', t:'ア' }` → `1|(2)|ア`
- `{ s:'1', t:'あ' }`（小問なし） → `1||あ`
- `{ s:'2' }`（小問も空欄も無い設問。H27-G1-1 の設問2「図2 中の①〜⑦の番号で答えよ」） → `2||`。
  設問文は `lead` を持たせず `heading: '設問2'` だけにする

> **注意: rowKey が重複する問がある。**
> `t` の無い同じ小問が複数行並ぶ問（例 **H29-G2-1** の設問1(2) は無ラベル4行）は、
> そのままだと解説・設問文の引き当てが壊れる。**その問に着手する前に `t` の付け方を決める**こと。
> `validate-data` が「要確認」として名前を挙げる。

## 3. 1問あたりの手順

### Step 1. 問題 PDF を精読する

PDF は画像スキャンでテキスト抽出できない。ページを画像化して目視で読む。
年度ごとに1ファイルで3問入り（同じ `questionPdfUrl`）。

```bash
SCRATCH="<セッションのスクラッチパッド>/pdf"
mkdir -p "$SCRATCH" && cd "$SCRATCH"
curl -sL -o q.pdf "<afternoonProblems[].questionPdfUrl>"
PYTHONIOENCODING=utf-8 python -c "
import fitz
d=fitz.open('q.pdf')
for i in range(d.page_count): d[i].get_pixmap(dpi=110).save(f'lo{i:02d}.png')
print(d.page_count)"
```

- まず dpi=110 の全ページを Read ツールで開き、**対象問の本文ページを特定**する（1問おおむね5〜6ページ）。
- 図表と設問文は細部が要るので、該当箇所を **clip して dpi=260〜520 で描き直して**読む:

```bash
PYTHONIOENCODING=utf-8 python -c "
import fitz
d=fitz.open('q.pdf')
p=d[<ページindex>]; R=p.rect
cl=fitz.Rect(R.x0+R.width*<x0>, R.y0+R.height*<y0>, R.x0+R.width*<x1>, R.y0+R.height*<y1>)
p.get_pixmap(dpi=260, clip=cl).save('fig.png')"
```

- 読み取るもの: 題材／〔　〕節の構成／下線①〜⑤の位置と内容／各設問文と字数条件／図表の全要素。
- **読み終えたら png と pdf を消す**（著作権）。消す前に、転記メモをスクラッチパッドのテキストに落としておく。

### Step 2. 公式解答・配点を確認する

```bash
PYTHONIOENCODING=utf-8 python -c "
src=open('src/data/officialAnswers.ts',encoding='utf-8').read()
i=src.find(\"id: '<問題id>'\"); j=src.find('},', src.find('],', i))
print(src[i-10:j+2])"
```

- `scoringMap.ts` の対象 id（`[correct, partial]` の配列。行順は `answers[]` と一致）。
- **高配点・記述式の行が難所** → `pitfall` を付ける対象。
- G1 は満点50点、G2 は100点。合計が合わなければ `validate-data` が落とす。

#### 公式解答データが実際の問題と合っているかを必ず照合する

**着手前に、問題 PDF の設問構成とデータの行構成が一致しているかを確かめる。**
H25〜H28 の午後Ⅰ 全12問は、データの中身が別問題だった（設問数すら合わなかった）。

解答例 PDF（`pdfUrl`）には**テキスト層がある**ので、機械的に照合できる。

```bash
PYTHONIOENCODING=utf-8 python -c "
import fitz
d=fitz.open('<解答例PDF>')
print(''.join(d[i].get_text() for i in range(d.page_count)))"
```

穴埋めの短答がデータと PDF で一つも一致しないなら、そのデータは別問題のもの。
その場合は **解答例 PDF どおりに `officialAnswers.ts` を書き直し、`scoringMap.ts` も行数を合わせて
推定し直す**（配点は IPA 非公表。穴埋め2点・数値3点・記述は字数に応じて5〜9点で合計を満点に合わせる）。
データ修正は独立したコミットにして、問題作成のコミットと混ぜない。

- **解答例が図の設問**（「図を完成させよ」「網掛け部分を分割し記入せよ」など）は、テキスト層に
  図の中身が出ない。ページを画像化して解答例の図を見て、**図の内容を文章に直して `a` に入れる**
  （例 H25-G1-3 の 2(3)「二つに分割し，前を TPID，後ろを TCI とする」）。配点は図で答える欄として3点前後。
  - 解答例の図で**太字の箱・太い線が描き足した所**になっていることがある（H26-G1-3 の 3(2)）。
    問題の図と見比べて、何が空欄で何を足したかを確かめてから文章にする
  - 描く要素が多い欄（H26-G1-3 の 3(2) は空欄3つ＋ゾーン転送の矢印2本）は、3点前後に収めず
    **要素の数に応じて重くしてよい**（8点にした）。記述を目安より下げずに50点へ合わせる逃がし先にもなる
- **`essay: true` を付けるかどうか**は、字数の条件の有無ではなく**答えの中身**で決める。
  答えが用語・名前（テーブル名・機能名・機器名）なら、字数の条件があっても付けない
  （H26-G1-2 の 2(2)「TCP の再送機能」・2(4)「MAC アドレステーブル」）。
  内容を自分の言葉で書く欄（作業の内容・理由・対策）は、15字以内でも付ける
  （H26-G1-3 の 4(1) b「ネットワークの切断」）。付けると解答欄が字数カウンタ付きの記述欄になり、行解説に `point` が要る。
- 表の形の解答例（フレーム①〜③の DA・SA など）は、行ごとに `t` ラベルを付けて分ける
  （`t: 'フレーム①'` のように、解答欄でそのまま読めるラベルにする）。
  H27-G1-2 の設問2(1) も同じで、図中の (A)・(B) ごとに「宛先 IP アドレス：機器 b，宛先 MAC アドレス：FW1」の
  1行にまとめ、`t: '(A)'`・`t: '(B)'` にした。1行に2項目あるので、短答より重めの4点にした。
- 解答例に「又は」がある欄（別解）は、既存データと同じく `X 又は Y` と書く（H26-G1-2 のウ・エ・オ）。
  文の別解は `A。（又は B。）` と1行にまとめる（H26-G1-2 の 3(2)）。
- **行が少ない問**（H27-G1-1 は11行）は、目安どおりだと合計が50点に届かない。穴埋めは2点のまま、
  図や本文から割り出す短答（図の番号・ドメイン名）を6点、25〜30字の記述を8点、40字を9点にして合わせた。
  名称だけを答える短答（ARP の名称）は3点に留める
- **同じ答えを何欄にも書く空欄**（H25-G1-1 のキ・ク・ケは3欄とも SSL-VPN 装置のアドレス）は、
  1つの理解で全部埋まるので **1点ずつ（`[1,0]`）** にして、合わせて短答1つ分の重みにする。
  記述の配点を目安（字数に応じて5〜9点）より下げずに合計50点へ合わせる逃がし先にもなる。

## 4. 公式設問文の転記（`questionTexts/<年度>.ts`）

```ts
{
  rowKey: '1|(2)|ア',
  heading: '設問1(2)',
  lead: '〔現状の配信方式〕について答えよ。',   // 親設問の導入文。小問が無い設問では省略
  text: '本文中の ア に入れる適切な字句を，本文中から選んで答えよ。…',
}
```

**年度ファイルが無い年度に着手するとき**は `questionTexts/<年度>.ts` を新設し、
`questionTexts/index.ts` の import とスプレッドに足す（`...r4,` のように年度順に並べる）。
これを忘れると設問文が画面に出ないが、`validate-data` は「設問文転記済み」の数で気づける。

### 守ること

- **原文を改変・要約しない。**要約は `detail.questionDetails.asked` の役割。混ぜない。
- **強調マークアップ（`==` / `__`）を入れない。**原文転記なので素のまま（`validate-data` が検出する）。
- 図表参照（「図1中の字句で」等）は原文どおり書く。参照先の図は §5 で同じ画面に用意する。

### 表記の決めごと（R6-G1-1 で確定）

| 原文 | 書き方 | 理由 |
|---|---|---|
| 囲み枠の空欄記号 | `本文中の ア に入れる` — **前後を半角空白で挟む** | 全角空白は lint の `no-irregular-whitespace` に落ちる |
| 英数字と日本語の境目 | `HTTP ではなく ICMP Echo で` — **半角空白を入れる** | `officialAnswers.ts` の IPA 引用データと同じ書き方 |
| 数字＋単位 | `50 字以内`／`図 2 中の字句` | 同上 |
| 読点・括弧 | `，` `．` `（）` は原文どおり全角 | |
| 下線・図中の番号 | `下線①の`／`下線（Ⅰ）で`／`図 2 中の⑥で` — **記号の前後に空白を入れない** | 丸数字・ローマ数字は日本語側の文字として扱う（H27-G1-1 は下線が（Ⅰ）〜（Ⅴ）） |

### 一つの小問が複数行にまたがるとき

設問1(2)（ア・イ）のように、1つの設問文が複数の解答行に対応する場合は、
**同じ原文を各行に持たせる**。文を切って分配しない（原文の改変になる）。
解答欄では行のラベル（ア／イ）が出るので、どちらを聞かれているかは分かる。

## 5. 図表の再現（`examFigures.ts` ＋ `components/afternoon1/figures/`）

### 5.1 方針

**IPA の図をビットマップで取り込まない（著作権）。同じ情報・同じ構造・同じラベルを自作 SVG で描き直す。**

- **範囲を絞らない。**問題が参照する図表はすべて再現する。「この図は難しいから省く」という判断はしない。
- **再現の水準**: ノード・リンク・本数・向き・ラベル・番号・凡例・注記まで、原図の情報を落とさない。
  設問が参照する記号（(a) 等）は原図と同じ記号・同じ位置関係にする。
- **レイアウトは 375px で読めるよう組み直してよい。**情報は落とさない。
  - 例（R6-G1-1 図1）: 原図は横一列だが、LB より先を下へ折り返した。
  - 例（R6-G1-1 図3）: インターネットを右端の縦長の雲にして、4つの ISP を接する形にした。
  - 例（H25-G1-1 図2）: 左から右へ流れる接続概念図を、**上から下へ流れる形**に組み直した。
    横一列のままだと文字が 5px 台まで縮むため。流れの線は右寄りに縦に並べ、最後に左へ折って
    サーバのポートに入れる。**折る順を「右の線ほど下で折る」にすると3本が交わらない**。
    組み直したら `note` に「原図は…。375px に合わせて…」と書き残す。
- **色は役割でしか変えない（§5.3）。**「目立たせたい」「彩りが欲しい」で色を変えない。
  強調は色を足すのではなく、解説を開いたときの赤（§5.6）でやる。
- 375px で実線と破線の区別が付かない箇所は、**色相ではなく濃さと線種**で分ける（`LOGICAL`）。
  凡例は原図どおり残す。

### 5.2 手順

1. `figureIds.ts` に id を追加（命名は `<問題id>-fig1` / `-tab1`）。
2. `figures/<Id>.tsx` を書く。共通部品は `figures/primitives.tsx`（描画）と `figures/tokens.ts`（色・`useFigureId`）。
3. `figures/index.ts` の `EXAM_FIGURES` に登録する。
   **`Record`（`Partial` ではない）なので、id を足して登録し忘れると型エラーになる。**
4. `examFigures.ts` に `{ kind:'exam', figureId, title, note, points }` を追加。
   `title` は原図の図題、`note` は原図の注記、`points` は §5.5 の解説。
5. `points` に対応する**強調**（経路・輪・吹き出し）を図に入れる（§5.6）。

**同じネットワークを2枚の図で見せる問**（R6-G1-3 の図1 と図3 のように、構成図に流れを重ねた図が続くもの）は、
**下絵のコンポーネントと座標ファイルを分けて共有する**。
`r6g13Layout.ts`（座標だけ・コンポーネント無し）と `R6G13Topology.tsx`（下絵）に分ければ、
`react-refresh/only-export-components` に引っかからずに2枚を同期できる。
下絵は `underlay`（線とノードのあいだ）と `overlay`（ノードの上）のスロットを持たせて、
強調を正しい描画順に差し込めるようにする。片方だけ座標がずれる事故がなくなる。

### 5.3 SVG を書くときの約束

- **viewBox 幅は 340 を基準にする。**モバイルの実表示幅はおよそ 280px。
  フォントは 8.5〜10 を目安（それ以下は読めない）。
- **文字の大きさは `FONT_SCALE`（`tokens.ts`）と `MAX_SCALE`（`primitives.tsx`）の2つで決まる。**
  各図が渡す `size` は図の中での大小関係を表すだけで、実際の描画は `size * FONT_SCALE`、
  さらに画面上では `MAX_SCALE` を上限とする倍率が掛かる。**座標は触らずに文字だけ動かせる。**

  | | 値 | 効き方 |
  |---|---|---|
  | `FONT_SCALE` | 1.2 | 図中の全文字に掛かる。**モバイルを読みやすくする側**のつまみ |
  | `MAX_SCALE` | 1.2 | 図の拡大の上限。**デスクトップで本文より大きくしない側**のつまみ |

  現在の実寸（本文は 13px）:

  | | 図の幅 | 倍率 | 図中の文字 |
  |---|---|---|---|
  | モバイル 375px | 283px | 0.83 | 8.5〜10px |
  | デスクトップ | 408px | 1.20 | 12.2〜14.4px |

  上限が無いと、デスクトップで図の枠が 640px 前後になり viewBox 340 が 1.9 倍に拡大されて、
  図の文字が 17〜19px と本文を大きく上回る（実際にそうなっていた）。
- **`FONT_SCALE` を上げると箱から文字がはみ出す。**1.3 では 図1 のサーバ名（2行）と
  囲みのラベルが枠に触った。**変えたら §5.4 の検査を必ず回す。**
- `<marker id>` は **`useFigureId()` でページ内一意にする**（同一ページに図が並ぶと衝突する）。
- **線はノードより先に描く。**線の端がノードに少し入り込んでも隠れるので、楕円の周上の座標を三角関数で出す必要がない。
- **同じノード対を結ぶ線が束になるときはレーンを分ける。**
  R6-G1-1 図3 の NetFlow 4本は、最初 6px 間隔で束ねたら矢頭が固まって読めなかった。
  折り返し位置（縦・横・縦）を本数ぶんずらして解決した（`FLOW_DROP_X` / `FLOW_LANE_Y` / `FLOW_RISE_X`）。
- **2段ヘッダの表は SVG で描かない。**HTML の `<table>` で組み、`overflow-x-auto` で横スクロールさせる
  （例 `R6G11Tab1.tsx`）。SVG より読みやすく、文字も選択できる。
  長い文が入る列（作業内容など）は `whitespace-nowrap` を付けずに折り返し、375px で表の中に
  横スクロールを出さない（H26-G1-2 表1。表は `w-full` と `maxWidth` で幅を決める）。
  **短い語の列は、語の途中で割れないよう折り返してよい所だけを決める**（H27-G1-1 表1）。
  何もしないと、長い列（URL）に幅を取られて「システ／ム名称」「現／状の／まま」のように割れた。
  `H27G11Tab1.tsx` の `Chunks` は `'営業|システム'` の `|` の所にだけ `<wbr />` を置き、塊は `whitespace-nowrap` にする。
  URL は「http://koukoku.」と「a-sha.example.jp」の2つの塊にして、その間でだけ折り返す
  （`a-sha` のハイフンで割れない。折り返すと共通のドメインが行頭にそろい、設問3(1) の手掛かりが見やすくなる）。
  余白は `px-1.5` に詰めた。
  **1つの行が複数の空欄の計算に効く表**（H27-G1-2 表1: 区間ごとの転送量を LB ごとに足す）は、
  マスを赤で塗るとどの空欄に効くかが分からない。解説を開いたときだけ、値の横に**赤の札**
  （その区間の通信が通る LB。`H27G12Tab1.tsx` の `TAG`）を出した。
- **図の注記が表を指している図**（H27-G1-2 図2 の注記2「各ルータのルーティング情報は次のとおりである」）は、
  注記と表を `note` に分けず SVG の中に置く。`note` は図の下に出るので、「次のとおり」の後に表が来なくなる。
  表のマスは枠と文字を1つの `<g>` にまとめ（`H27G12Fig2.tsx` の `Cell`）、§5.4 の検査2 で余白を測れるようにする。
- **色は役割だけで決める。`tokens.ts` の `TONE` の3つから選ぶ。**
  `Box` / `Ell` の `tone` には既定値が無いので、必ずどれかを選ぶことになる。

  | tone | 何に使うか | 例 |
  |---|---|---|
  | `device` | 自社側のネットワーク装置・自社の網 | ルータ／L2SW／L3SW／LB／FW／SD-WAN装置／BGPルータ／自社の AS |
  | `host` | サーバ・PC・端末 | 配信サーバ／プロキシサーバ／DDoS検知サーバ／PC／ゲーム端末 |
  | `outside` | 自社の外にあるもの（他社の網・他社の装置） | インターネット／ISP／IX／他社の AS／MPLS VPN／PE／SaaS |

  **ネットワーク構成図でない図（パケット構造・状態遷移など）には、この3色を当てない。**
  役割で説明できない色は使わないのが原則なので、マスを全部同じ白にして、
  入れ子や並びだけで意味を持たせる（R6-G1-3 図2 がその例）。
  手順を枠で囲んで並べた図（H26-G1-3 図3 の「発見者の対応」と「セキュリティ担当者の対応」）も同じで、
  白の枠に文字を並べる。**2つの手順を見比べさせる図は、375px でも横並びを崩さない**
  （縦に積むと、担当者にだけある段が見比べられなくなる）。表ではないので HTML ではなく SVG で描いた。

  **シーケンス図**（H27-G1-1 図2）も3色を当てない。縦線は `LINE`、メッセージの矢印は `LOGICAL`。
  PC がかかわる矢印の文言は PC と次の縦線のあいだに、サーバどうしの矢印の文言はサーバの縦線のあいだに置く
  （長い矢印の文言を真ん中に置くと、途中の縦線に重なる）。2本で1組の矢印をくくる波括弧は `path` で描く
  （`H27G11Fig2.tsx` の `Brace`）。番号（①〜⑦）は縦線の左の外に置く。

  **原図の重ね書き**（Web サーバ3枚・DNS サーバ2枚のような複数台の表現）は、枚数まで原図に合わせる。
  設問が「DMZ に2台、内部に3台」のような台数を使うことがある（H26-G1-3 図1 と図2 の DNS サーバ）。
  `H26G13Fig1.tsx` の `Stack`（後ろの枚数を渡す）と、横倒しの円筒の `Drum`（データベース）が使える。

  **原図の網掛け**（「網掛け部分は追加した機器を示す」のように注記で意味が付いたもの）は、
  役割の色を変えずに、**箱の上に細い斜線を重ねて**残す（H25-G1-1 図1 の `HatchBox`。
  斜線は `<pattern>` で描き、id は `useFigureId()` で一意にする）。色を足すと役割の色と区別が付かなくなる。
  フレームの並びの図のように役割の色を当てない図では、網掛けは薄い灰色の塗りでよい（H25-G1-3 図2）。

  **同じ役割のものは必ず同じ色になり、色が違えば役割が違う**、という状態を保つ。
  FW だけ赤、BGP ルータだけ紫、のように理由の無い色分けをすると、
  読み手が「なぜここだけ違うのか」を考えてしまう（実際にそう指摘を受けて作り直した）。
  PE は **L 社（キャリア）の装置なので `outside`**、というように、
  持ち主で決まる境目があることも覚えておく。
- **線の色は2つだけ。**物理的な接続線は `LINE`、
  論理的な関係の線（BGP ピア・NetFlow の送信方向など）は `LOGICAL`。
  `LOGICAL` は `LINE` より濃いだけで色相は同じ側にあり、**破線と矢印で見分ける**。
  DNS の問合せとゾーン転送だけでできた概念図（H26-G1-3 図2）は、矢印がすべて `LOGICAL` で、
  原図の凡例どおり実線（問合せ）と破線（ゾーン転送）で分ける。矢印の先は箱の縁にぴったり置き、
  楕円に刺さる矢印は楕円の式で縁の座標を出す（線はノードより先に描くので、中に入れると矢頭が隠れる）。
- 赤（`MARK` / `MARK_FILL` / `MARK_TEXT`）は**強調専用**。図の常時表示には使わない。
- **描く順番を守る。囲み → 線 → 強調（経路・輪）→ ノード → 強調の文字。**
  強調の経路と輪をノードより先に置くので、**箱の中の文字に重なりようがない**。
  ノードを先に描いてしまうと、あとから重ねた赤がラベルを潰す。

### 5.4 図が崩れていないかの検査（`FONT_SCALE` や座標を触ったら必ず）

目で見るだけでは「箱の上辺に文字が触っている」のような詰まりを見落とす。
Browser pane の `javascript_tool` で、全 `<text>` の bbox を親の箱と viewBox に突き合わせる。
回転した文字（図3のインターネット）があるので、`getScreenCTM()` で座標系を揃えてから比べること
（`getBBox()` だけだと回転前の値が返り、誤検出する）。

**強調（§5.6）を入れたら、解説を開いた状態でも必ず回す。**
吹き出しは文字を持つので、閉じた状態が通っても開いた状態で壊れうる。

見るもの:
1. **viewBox からのはみ出し** — `x < 0` / `y < 0` / `右 > 幅` / `下 > 高さ`
2. **親の箱からのはみ出し** — `<g>` の中の `<rect>` と text の bbox を比べる。
   **余白が 1px 未満なら詰まり過ぎ**として直す（0 を割っていなくても、枠線に触って見える）
3. **文字どうしの重なり** — 同じ図の text の bbox を総当たりで交差判定する
   （凡例の2つのラベルが接する、といった事故を拾える）
4. **あとから描かれる不透明な図形が、先に描かれた文字を覆っていないか** — 全要素をツリー順に並べ、
   `fill` が `none` でない `rect` / `ellipse` / `circle` と、
   **それより前にある** `<text>` の bbox を突き合わせる。
   吹き出しが既存のラベルを隠していないか（ユーザからの明確な要求）を、これで機械的に担保する。
5. **強調の経路が実在の線・ノードの上を通っているか** — 赤い `polyline` を 4px 刻みで標本化し、
   各点が「ノードの箱・楕円の内側」か「既存の `line` / `polyline` から 2.5px 以内」かを確かめる。
   1点でも外れたら、**原図に無い経路を勝手に描いている**ということなので、
   実配線の折れ点を頂点に足して沿わせ直す。

5つとも 0 件になるまで直す。R6-G1-1 / R6-G1-2 の9図は、
**閉じた状態・開いた状態の両方**・375px とデスクトップ幅の両方で 0 件になっている。

検査5の対象は**経路**（`Route`）だけ。範囲の帯（`RangeBar`、`data-role="range"`）と
解答の描き込み（§5.6、`data-role="answer"`）は外す。描き込みの線は代わりに
**両端が既存の箱か描き込みの箱の中に入っているか**を確かめる。

検査スクリプトを書くときの注意（H25-G1-1 で踏んだもの）:
- **楕円（インターネット・ISP など）の内側もノードとして扱う。**扱わないと、雲を通る経路が
  すべて「配線から外れた」と誤って報告される
- 吹き出しの引出し線を検査5 から外すときは、**同じ `<g>` に `rx="3"` の rect と text がある
  polyline だけ**にする。親の要素の子に角丸の rect があるだけで外すと、凡例の角丸に反応して、
  図の直下に置いた本物の経路まで検査から漏れる

**検査のコードは `docs/afternoon1_figcheck.md` に置いてある**（H25-G1-2 で追加）。毎回書き直さず、そこから貼る。
解答欄では「答え合わせ」→ 確認ダイアログの「はい」で checkMode に入れてから測る
（入れないと図の「解説」ボタンが出ず、開いた状態を測れない）。

**「PC … PC」の「…」は全角 1em ある。**同じ組の箱のすき間は 16px 取る
（H26-G1-2 で 10px にしたら、後ろの PC の箱が「…」に 0.1px 掛かって検査4 に拾われた）。

**文字の箱は Meiryo UI で測ると思ったより高い**（1行でおよそ 1.38em）。H25-G1-3 で踏んだもの:
- size 7 の2行（Ether Type/Length）は、高さ 22 のマスに入らない（文字の箱が 21.6）。**27 にした**
- 共通の `RouteTag`（高さ fs+6）は、文字の箱と札の上辺の余白が 0.3px 程度しかなく、検査2 で拾われる
  （既存の R6-G1-1 図1 の札も同じ）。新しい図で札を使うときは、高さ fs+8 の札を図の中に持つ
  （`H25G13Fig2.tsx` の `BitTag`）。共通部品を直すなら、全図を測り直してからにする
- 同じ図でも 375px では 0 件、1024px では2行ラベルの行間が 0.33px 重なる、ということが起きた。
  **幅を変えるたびに測り直す**（倍率で文字の箱の丸めが変わる）

H26-G1-3 で踏んだもの:
- **文字の幅は `estimateWidth`（全角 1.0em／半角 0.55em）と合わない。**Meiryo UI の実測では、
  全角はおよそ 0.82em と見積もりより狭く、**英大文字はおよそ 0.7〜0.76em と見積もりより広い**
  （size 7.5 で「DMZ」が 20.4、「DNS-S」が 30.8）。英大文字の多い吹き出しの行（「DMZ の DNS-S は」）は、
  文字の幅が見積もり 72 に対して実測 79 あり、吹き出しからはみ出した。吹き出しの幅は置いてから実測で決める
- **枠で囲んだ空欄の記号**（図3 の b）は、size 7.5 だと文字の箱がベースラインの 10 上から 2.5 下まである。
  枠をベースラインの 12 上から取ると上の余白が 1.3px で検査2 に拾われたので、**13 上から 6 下まで（高さ 19）**にした
- 検査2 は、文字と同じ `<g>` の rect・ellipse だけを親の箱として測る。円筒のように `path` で描いた図形の中の文字は
  測られないので、**文字の置き場に `fill="none"` の rect を同じ `<g>` に置いて**余白を測らせる（`Drum`）。
  塗りが無い rect は検査4 と検査5 の対象にならない
- 文字の無い箱（図2 の空欄）は、`Box` に空の `lines` を渡さず rect だけで描く。
  中身の無い `<text>` を作ると、大きさ 0 の文字の箱が測定に混ざる

H27-G1-1 で踏んだもの:
- **見出しを2行に分けて `Cap` で置くときは、ベースラインを 13.5 以上離す**（size 7.5）。
  「Web アプリケーション／サーバ」を 12 離したら、行どうしが 0.45px 重なって検査3 に拾われた
  （`Box` の2行は行間 fs+2.5 で組まれるので、この問題は起きない）
- 吹き出しの英字は、ここでも見積もりより広かった。「Domain 属性があれば」は見積もり 81 に対して実測 91.7。
  縦線に挟まれて幅に上限がある所では、文言を短くして収める（「Domain 属性で Cookie を Web サーバにも送らせる」
  から「Domain 属性があれば Web サーバにも届く」にした）

H27-G1-2 で踏んだもの:
- **size 7.5 の2行の箱は高さ 30 にする。**28 だと上下の余白が 1.2px で検査2（詰まり気味）に拾われた
  （「社内メール／サーバ」「Web／サーバ」など4か所）。size 7 の2行は 27 でよかった（H25-G1-3）
- 「機器a」のような全角2字＋英字1字の箱は、幅 30 だと左右の余白が 1.2〜1.3px で詰まる。33 にした

### 5.5 図の解説（`points`）

図を載せるだけでなく、**どこに注目すれば設問が解けるか**を 2〜3件 付ける。
図の下に「解説」ボタンで開閉する（既定は閉じ）。**開くと同時に、図の該当箇所が赤で強調される（§5.6）。**

- 1件 40〜80字。`==赤==` / `__ネイビー__` を使ってよい（1件2ペアまで）。
- **設問番号を添えて具体化する**（例「==この変わり目==がサーバ証明書の置き場所を決める（設問1(3)）。」）。
- 書くこと: 図の記号の意味（実線と破線の違い等）／原図の作図の含み（箱の重ね書き＝複数台）／
  設問が比べさせたい2つがどこに描かれているか。
- **解答に触れてよい。**ただしそのぶん表示を絞っている（下記）。

> **表示の制御**: `points` は設問の答えに触れるので、
> **解答欄では答え合わせ（checkMode）に入るまでボタンが出ない**。詳細解説ページでは常に出る。
> `Afternoon1FigureView` の `allowPoints` プロパティで制御していて、
> 解答欄は `allowPoints={checkMode}`、詳細解説ページは既定の `true`。
> 「書く → 採点 → 解説」の順序を崩さないための作り。
> **強調も同じボタンに連動する**ので、採点前の解答欄には赤が一切出ない。

### 5.6 強調（解説を開いたときだけ図に重ねる書き込み）

`points` が言葉で説明している箇所を、**図の上でも指す**。
図コンポーネントは `ExamFigureProps`（`highlight?: boolean`）を受け取り、
`true` のときだけ赤を重ねる。閉じているときは原図どおりで、赤は1つも出さない。

| 部品 | 何をするか | 置く場所 |
|---|---|---|
| `Route` | 経路を太い赤でなぞる。`soft` で「選ばれない方」を細く薄く描ける | **ノードより前** |
| `Ring` / `RingEll` | 箱・楕円のまわりに赤い輪を敷く | **そのノードより前** |
| `RouteTag` | 経路の上に置く小さな札（`HTTPS` など）。線だけを隠す | ノードより後 |
| `Callout` | 吹き出し。`leader` で対象を指し、先端に丸が付く | ノードより後 |

書くときの約束:

- **1つの図に吹き出しは2つまで、輪は3つまで。**全部を指すと、どれも指していないのと同じになる。
- **`Route` は実在の配線をなぞる。**空いている所を突っ切らない。
  既存の `Wire` の折れ点を頂点に入れると自然に沿う（§5.4 の検査5が外れを拾う）。
  シーケンス図の矢印をなぞるときは、**矢頭の手前（8px）で止める**（H27-G1-1 図2）。
  太い赤を矢頭まで引くと、どちら向きの矢印かが見えなくなる。
  1本の線を行って戻る道筋（LB へ行き、同じ線で SW2 へ戻って SSO サーバへ。H27-G1-1 図1）は、
  2本の `Route` に分けてよい。重なった区間は1本に見える。
- **`Callout` は空いている場所にしか置けない。**置いたら §5.4 の検査4で、
  既存の文字を1px も隠していないことを確かめる。**隠すくらいなら吹き出しを諦める**
  （R6-G1-2 図1 の「ルータ3 ⇔ PE3」は、枠に収まらなかったので輪と経路だけにした）。
- **`points` と強調を食い違わせない。**文章が「LB11 が攻撃対象」と言っているなら、
  図でも LB11 に輪と吹き出しを付ける。どちらかだけ直して片方を放置しない。
- 文字の大きさの既定は `size = 7.5`（`* FONT_SCALE` で 9）。
  モバイルで 7.5px、デスクトップで 10.8px になり、本文（11.5px）より少し小さい。
  **これより小さくしない**（6.5 だとモバイルで 6.5px になり読めなかった）。
- 表（`Tab*.tsx`）も同じ `highlight` を受け取る。該当のセルに
  `bg-red-50 text-red-700 font-bold ring-2 ring-inset ring-red-500` を足す。
- **2台1組を囲む輪は、線より先に敷いてよい。**組を結ぶ横線（スタックの接続など）を
  輪の塗りで隠さないため（H25-G1-3 図1）。文字を隠さないという目的は変わらない。
- **同じことが言える箱が複数あるときは、1つを指す吹き出しにしない。**H26-G1-3 図2 の
  「キャッシュ無効」は DMZ の DNS-S 2台（空欄も含む）に当てはまるので、1台に引出し線を引かず、
  **引出し線の無い吹き出しを DMZ の枠の中に置いて**「DMZ の2台は」と書いた。
- 手順を並べた図では、**段（文字の行）に輪を付けてよい**（H26-G1-3 図3 の (6)）。輪は枠の後・文字の前に敷く。

#### 図で答える設問は、解答例の図を赤の破線で描き込む

「図3 を完成させよ」「網掛け部分を分割し記入せよ」のように**図そのものが答えの設問**は、
解説を開いたときに、解答例の図の部分（描き足す箱と線・分割線とフィールド名）を**赤の破線**で重ねる
（H25-G1-3 の図2・図3）。閉じているときは原図どおりで、描き込みは一切出さない。

- 描き込みの要素は `<g data-role="answer">` で包む。経路ではないので §5.4 の検査5 から外れる
- 描き込みの線は、両端が既存の箱か描き込みの箱の中にあることを実測で確かめる
- 描き込みの文字も強調の文字なので size 7.5 以上。入るマスの幅はそれに合わせて取る
  （H25-G1-3 図2 は網掛けを TPID が半分に入る幅にした）
- `points` の1件で「赤の破線が設問X で描き足す部分」と書き、描き込みと文章を対応させる
- **空欄の箱を埋める設問**（H26-G1-3 図2 の空欄の DNS サーバ）は、空欄と同じ位置・大きさの赤の破線の箱と
  答えの文字を1つの `<g>` にして、ノードの後に重ねる。空欄には文字が無いので、上に重ねても検査4 に掛からない。
  描き足す矢印は `<line>` に赤の矢頭を付け、ノードより先に描く

図の色が何を表しているかは、`Afternoon1FigureColorKey` が図表セクションの先頭に1回だけ出す
（解答欄・詳細解説ページの両方）。図ごとに凡例を繰り返さない。

### 5.7 比較表（`detail.figures` の `compare`）

解説用の対比整理。試験図とは別物。

- 列は **観点列＋3列まで**（`columns.length <= 4`）。`validate-data` が検出する。
- `label` が長いと右の列が潰れる。**正式名称は意味の列に逃がす**
  （例: `LP（LOCAL_PREF）` を `LP` にして、意味の列を `LOCAL_PREF。自 AS 内で…` にした）。
- 上限の4列でも、375px では1列が3行に折れて読みにくいことがある（H26-G1-3 の「置き場所」列で
  「内部セグメント」が3行になった）。**短い値しか入らない列は `label` にまとめて**3列に減らす
  （`DNS-S（DMZ に2台）` のようにした）。実機の 375px で表を見てから決める。
- **設問の答えがそのまま列として読める形に組む**と学習価値が高い
  （例「DDoS を止める3つのやり方」は、止める場所の列＝設問3(1)、選別できる条件の列＝設問3(2)）。

## 6. 行解説（`overview` ＋ `rows[]`）

答え合わせ画面で、各解答例の直下にアコーディオンで出る。**採点直後に「自分の解答のどこが足りないか」が分かる**のが役割。

### 6.1 `overview`

「**状況 → ぶつかる難所 → 何が問われるか**」の流れで書く。設問の平板な列挙にしない。目安100〜200字。

### 6.2 `rows[]` — 厚みを2段階に分ける

NW は用語・数値の穴埋めが多く、全行に同じ厚みで書くと冗長で読みにくい。

| 行の種類 | `point` | `basis` | `knowledge` | `reasoning` | `pitfall` |
|---|---|---|---|---|---|
| **記述式**（`essay: true`） | **必須** | 必須 | 付ける | 必須 | 難所に付ける |
| **用語・数値の穴埋め** | 省略する | 必須 | 付ける | 必須 | 取り違えやすい行に付ける |

`validate-data` が「記述式なのに `point` が無い」を検出する。

| フィールド | 役割 | 字数目安 |
|---|---|---|
| `point` | この設問が**何を問うているか**（力点・解答の方向） | 30-60字 |
| `basis` | **本文のどこが根拠か**（位置参照＋言い換え。逐語引用しない） | 40-90字 |
| `knowledge` | **この行を解くのに要る技術知識** | 40-80字 |
| `reasoning` | **なぜその解答例になるか**（論理） | 60-120字 |
| `pitfall` | ありがちな失点・誤答 | 40-80字 |

### 6.3 `knowledge` を分けて持つ理由（NW 固有）

PM 午後Ⅰは `basis`（本文の位置参照）だけで根拠が立つ。
**NW は「本文のこの記述」＋「プロトコルの仕様知識」の両方が要る行が大半**なので、分けて持つ。

- `basis` … 本文・図表のどこを見るか（位置参照＋言い換え）
- `knowledge` … それを解くのに要る仕様の知識（ICMP と HTTP の層の違い、LP と MED の向き、IX が AS Path に現れないこと 等）

**穴埋め行でも `knowledge` は付ける。**穴埋めこそ知識で決まるため。
UI では `本文の根拠` の下に「必要な知識」として teal 色で出る。

### 6.4 `basis` の書き方

位置参照＋言い換え。逐語引用しない。

- ○ 「〔現状の配信方式〕の下線①で、LB が配信サーバの生死を HTTP のアクセスで確かめ、止まっているサーバには振り分けないと説明している。」
- ○ 「表1に、ゲームごとの配信サーバの所属セグメントが載っている。ゲームβの行を見ればよい。」
- ✕ 本文の文をそのまま写す。

### 6.5 質の基準（2026-09-24 ユーザ指示。H25-G1-3 から適用）

既存の問を上回るために、各フィールドで次を守る。

| フィールド | 基準 | 避けるもの |
|---|---|---|
| `basis` | 本文の**どこを見るか**（節・段落・下線・図の位置）に留める | 原文の言い回しを残した要約。書いたら転記メモの特徴的な句と機械的に突き合わせる |
| `knowledge` | **その行を解くのに本当に要る仕様**だけ | 一般論の水増し（その行の判断に使わない説明） |
| `reasoning` | **なぜその解答例になるか**の論理（手掛かり → 判断 → 答え） | 解答例の言い換えで終わること |
| `pitfall` | **実際に書かれやすい誤答を名指し**して、なぜ違うかを書く | 「よく考えること」のような空語 |
| 記述式の行 | **核の要素**を挙げ、**何が欠けると部分点止まりか**を具体的に書く（`pitfall` と `commentary`） | 「具体的に書く」だけの助言 |

**書き終えたら `docs/afternoon1_textcheck.md` のスクリプトで機械的に確かめる**（H27-G1-1 で追加）。
マークアップ・字数の目安・転記メモの特徴的な句との一致・メモの本文との最長一致を一度に見られる。
特徴的な句は0件、最長一致は節の名前や固有名詞だけになるまで言い換える。
字数は長い固有名詞（ドメイン名・URL）で膨らみやすいので、`reasoning` などでは「営業サーバと広告サーバ」のように言い換える。

`thinkingProcess` は**解答を知らない状態から辿れる**順にする。1段目で答えを言わない。

## 7. 詳細解説（`detail`）

腰を据えて復習するためのページ。

### 7.1 `problemSections`（問題文の解説）

**本文のセクション構成どおりに区切る。**（導入）／〔　〕節ごとに1ブロック。

- 本文そのものはアプリに載せないので、**このブロックが本文理解の受け皿**になる。
- **各ブロックの末尾に、どの設問の根拠かを明記する。**ここが詳細ページの学習価値の核心。
  例: `→ 設問1(1)は下線①、設問1(2)アは振分けの条件、設問1(2)イは表1、設問1(3)は 443 と 80 の変わり目がそれぞれ根拠。`
- 段落区切りは `\n`。

### 7.2 `questionDetails`（設問別の詳細解説）

解答行と **rowKey で 1:1**（欠落も余剰も不可。`validate-data` が突合する）。

| フィールド | 中身 |
|---|---|
| `heading` | 「設問1(2) ア」等の表示見出し |
| `asked` | 設問が問うていることの**要約**＋字数条件（原文は `questionTexts/` にある） |
| `thinkingProcess[]` | **解答に至る思考の手順**（3〜5ステップ）。「設問が問うのは何か → 本文/図のどこを見るか → どう導くか → 解答表現」の順 |
| `modelAnswer` | 解答例。**`officialAnswers` と一致させる**（複数解答は `／` 連結）。マークアップは入れない |
| `commentary` | 根拠・なぜその解答か・部分点や失点の機微。配点に触れると重みが伝わる |

`modelAnswer` が公式解答例とずれていると `validate-data` が「要確認」に出す。

### 7.3 `keyKnowledge`

その問で習得すべき知識を `term` ＋ `description` で **4〜6件**（範囲外だと `validate-data` が「要確認」に出す）。
プロトコルの仕様だけでなく、解法の観点（「死活確認は"どの層まで確かめるか"で精度が変わる」等）も入れてよい。

### 7.4 `solvingTips`

**その問固有の知識ではなく、ほかの午後Ⅰにも転用できる型**に限る。3件前後。

例（R6-G1-1）:
- 「A ではなく B にしたらどんな問題があるか」→ A と B が見ている**層の違い**を探す。
- 「図○中の字句で答えよ」→ 答えは必ずその図に書かれた語。先に図の語を拾って候補を絞る。
- 「A と比較した B の長所」→ **先に A の弱点を言語化**してから、その裏返しを書く。

## 8. マークアップ規約

描画は `src/components/afternoon1/MarkupText.tsx`。

- `==重要語==` → **赤太字**（`text-red-600`）。解答の核心・暗記対象。
- `__構造ラベル__` → **ネイビー太字**（`#1a3a5c`）。本文の参照箇所・段階名・構造のラベル。
  - ノートモードの `RedWord` / `NavyWord` と同じ色。PM 側のブランド紫（`#9d5b8b`）は使わない。

### 量と書き方

- **1フィールドあたり `==` は2ペアまで、`__` は2ペアまで。**`validate-data` が検出する。
- **開閉は必ずペア。**`==x__` のような食い違いは禁止。
- **全角イコール `＝` は使わない。**半角の `===` も禁止。
- **入れ子にしない。**`__…==x==…__` は描画が壊れる。
- **マークアップの直後に半角空白を置かない。**
  `==AS Path 長だけで決まる== 状態` と書くと「決まる 状態」と助詞の前が空く。
  英数字で終わる語（`==LB==。`）の前後の空白は、§4 の表記ルールどおり入れてよい。
- `modelAnswer` と公式設問文の `text` にはマークアップを入れない。

適用先: `overview` ／ `rows[]` の全フィールド ／ `detail` の全テキスト（`problemSections.body`・`asked`・`thinkingProcess`・`commentary`・`keyKnowledge.description`・`solvingTips`・比較表の `columns`/`cells`/`label`/`note`）。

> **`validate-data` は `detail` 配下も含めて全文字列を走査する**（PM 版は `rows`/`overview` しか見ておらず、量産中に開閉ミスを頻発させた。NW 版ではその穴を塞いである）。

## 10. つまずいた所（実際に踏んだもの）

- **`cat >` でファイルを丸ごと書き換えると Vite の HMR が壊れる。**
  画面が真っ白になる／`does not provide an export named ...` が出たら、
  `preview_stop` → `preview_start` で直る（ソースは正しい。`npm run build` が通るかで切り分ける）。
  編集は Write / Edit ツールを使うほうが安全。
- **CRLF。**既存ファイル（`Home.tsx` など）は CRLF。Python で読み書きすると LF に落ちる。
  `open(p, encoding='utf-8', newline='')` で読み書きし、既存ファイルを触ったら
  `git diff` が意図した行だけになっているか確認する。新規ファイルは LF でよい。
- **全角スペース（U+3000）は lint エラー。**図題を `図1　D社…` と書くと `no-irregular-whitespace` で落ちる。
  半角スペースにする。
- **`primitives.tsx` に定数やフックを置くと `react-refresh/only-export-components` で落ちる。**
  コンポーネント以外は `tokens.ts` に置く。
- **SVG の `<marker id>` 衝突。**同一ページに図が並ぶので `useFigureId()` を必ず使う。
- **一時スクリプトは `scripts/_*` に置き、commit 前に必ず消す**（lint が拾う）。
- **Browser pane のスクリーンショットが取れなくなることがある**
  （"page did not finish rendering"）。図の検証は目視に頼らず §5.4 の実測で回す。
  実測のほうが「1px の重なり」を確実に拾えるので、取れない日でも品質は落ちない。
- **ビューポートの emulation を `desktop` に戻すと幅が 0 になることがある。**
  そのまま測ると全要素が「viewBox の外」と報告される。
  デスクトップ幅で測りたいときは `resize_window` で 1024x800 のように明示する。
- **別のチャットが 5173 の dev サーバを使っていると `preview_start` できない**（このセッションの
  Browser pane からは他チャットのサーバに届かない）。`.claude/launch.json` に
  `"runtimeArgs": ["node_modules\\vite\\bin\\vite.js", "--port", "5181", "--strictPort"]` の設定を
  **一時的に**足して起動する。launch.json は git 管理下なので **commit せず、作業後に戻す**。
- **localhost で開くとログイン画面に飛ぶ。**パスワードは入れず、教科書の検証と同じく
  `localStorage['nwsp:auth']` に開発用のセッション（userId・loggedInAt・expiresAt）を置いてから開く。
  Browser pane を開き直すと消えるので、そのたびに置き直す。
- **Git Bash のヒアドキュメントに Python を書くと、バックスラッシュが崩れることがある**
  （`\\P` が `\P` になって SyntaxWarning、正規表現の `[^'\\]` が壊れる）。
  検査スクリプトはスクラッチパッドにファイルで書いて実行する。
- **実測の関数はリロードで消える。**`localStorage` に関数の文字列を退避しておき、
  リロード後に `(0, eval)(localStorage.getItem(...))` で戻すと、幅を変えるたびに貼り直さずに済む。
- **clone し直した直後の `npm install` は ERESOLVE で止まる**（2026-09-26、E: へ移したとき）。
  `@zxing/browser@0.2.0` の peer は `@zxing/library@^0.22.0` だが、package.json とロックファイルは 0.23.0 を指している。
  ロックファイルはこの組み合わせで作られているので、**`npm ci --legacy-peer-deps`** でロックファイルどおりに入れる
  （package.json もロックファイルも書き換わらない）。`--force` や `npm install --legacy-peer-deps` でロックファイルを作り直さない。
- **解答欄で「○」を押して配点を確かめたら、`nwsp:a1:draft:<id>` を消しておく**（Browser pane の localStorage に残る）。
- **スクリプトで `explanations.ts` を丸ごと書き直すと、HMR のエラーがコンソールに残る**（H27-G1-2）。
  「does not provide an export named 'getAfternoon1Explanation'」が出るが、ソースは正しい（`npm run build` が通る）。
  `preview_stop` → `preview_start` で起動し直したあとも、`read_console_messages` は**前の記録を返し続ける**ので、
  同じ `?t=` の番号のエラーは古いものと見てよい。確かめるなら、最新の数件（`limit`）だけを読むか、
  ページから `await import('/src/data/afternoon1/explanations.ts')` で export を読んでみる。
  起動し直した直後のログに「[scoring] 配点整合性チェック OK（60 問）」が出ていれば、配点データも読めている。
